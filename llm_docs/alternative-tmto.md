# 代替案: 時間空間トレードオフ(Hellmanテーブル / レインボーテーブル)

## 1. 概要

一方向関数の逆算に用いられる古典的な時間空間トレードオフ(TMTO)を適用する方式。
数百MBのテーブルで全2^32状態を確率的にカバーし、クエリ時に一定の計算を行う。

## 2. 定式化

関数fを次のように定義する。

```
f(s) = s を起点とする 7 バトル分のコード列 (c₁..c₇) を整数化した値
       K = Σ cᵢ·24^(7-i) を 32 bit に縮約したもの
```

fは32bit→32bitの擬似ランダム関数とみなせる。
観測からKが得られるため、「f(s) = Kなるsを求める」という関数逆算問題に帰着し、TMTOが適用できる。

チェーン構成(レインボーテーブル、チェーン長t、チェーン本数m):

- 縮約関数Rᵢ(列位置ごとに異なる)でfの出力を次の入力に写す
- テーブルには各チェーンの始点・終点のみを保存する

パラメータ例: t = 2^8、m = N/t = 2^24とすると、テーブルは2^24 × 8B = **128MB**。

## 3. コスト解析

### クエリ

- 探索: 最大t回の再構築 × 平均t/2回のf評価 ≈ t²/2 = 32,768回
- f1回 ≈ 7バトル ≈ 9,000消費であるから、約3×10⁸ステップ
- シングルスレッドで **0.1〜0.3秒**(偽陽性の検証で2〜3倍のばらつきあり)
- 列単位で独立なため並列化は容易

### テーブル生成

- m × t = N回のf評価 ≈ 2^32 × 9,000 ≈ 3.9×10¹³ステップ
- 16スレッドのCPUで30分前後、GPUなら数分
- ただし単一テーブルの被覆率は理論上80%台で頭打ちになるため、実用的な成功率(99%以上)には複数テーブルまたは余裕を持たせた構成が必要であり、生成コストとメモリは数倍(**256〜512MB、CPU数時間**)を見込む

## 4. 評価

### 長所

- 全2^32を対象としつつテーブルが数百MBに収まる(像への制限や観測の先頭1回の破棄が不要)
- 逆算問題としての定式化は汎用的で、他タイトルへの転用が利く

### 短所

- 検索成功が確率的(テーブルを増やしても100%にはならない)
- クエリレイテンシ0.1〜0.3秒は、圧縮LightDB案(数ms)に対して2桁劣る
- 偽陽性の除外・縮約関数設計・複数テーブル管理など実装の複雑さが最も高い
- メモリを実用水準まで積むと、結局サイズが圧縮LightDB案(約450MB)と同等になる

## 5. 結論

検索が確率的に失敗するのは論外。
