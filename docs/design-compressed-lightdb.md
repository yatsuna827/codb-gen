# LightDB圧縮フォーマット 設計・見積

## 目的

ポケモンコロシアム「とにかくバトル」による現在seed特定に用いるLightDBについて、検索レイテンシ1クエリ1秒以内を満たしつつストレージサイズを削減する。

## 前提

### 観測モデル

- 対象: とにかくバトル(シングル・最強)
- 1回の観測で得られる情報: COMトレーナー名(3通り) × 自パーティ(8通り) = 24通り ≈ 4.585bit
- 敵チームは画面に表示されないため観測に使用できない
- LCGの状態空間は2^32であり、log₂₄(2^32) ≈ 6.98から理論上7回の観測で特定可能
- 運用上は8回観測し、先頭1回分を捨てて後ろ7回分をキーとする

### LightDBの意味論(実測値)

| 項目 | 値 |
|---|---|
| エントリ数 | 128,095,165 |
| 値の意味 | キーになっている7回分のチームの**生成後**のLCG状態(検索結果をそのまま現在seedとして使用可能) |

キーの計算起点は「観測1戦目開始時点の状態」だが、エントリに記録されているのは起点ではなく生成後の状態である点に注意する。

## フォーマット仕様

単一ファイル構成とする。インデックスを表セクションに陽に持つ。

キーの定義: 観測1〜7戦目のコードc₁..c₇(各[0,24)、c = トレーナー名 × 8 + チーム)に対し

```
K = c₁·24⁶ + c₂·24⁵ + c₃·24⁴ + c₄·24³ + c₅·24² + c₆·24 + c₇
P = ⌊K / 576⌋   (プレフィックス: c₁..c₅、24⁵ = 7,962,624 通り)
R = K mod 576   (剰余: c₆, c₇、10 bit で表現可能。ファイルには保存しない。
                 検索時は前向きシミュレートの全照合で判別する)
```

圧縮LightDBには表セクションの形式が異なる**CUML(累積形式)**と**CNTS(個数形式)**の2種類があり、どちらを使うかはファイルサイズと検索コストのトレードオフで選ぶ。
ヘッダはmagic("COLIGHT\0")で両形式共通のファミリーを識別しつつ、format(FourCC "CUML"/"CNTS")で形式を、version(形式ごとに1から採番)で形式内の改訂を表す。

ファイルレイアウト(リトルエンディアン、両形式とも「ヘッダ+表セクション+部分seed配列」の3セクション構成で、表セクションの内容だけが異なる):

**ヘッダ(64B、両形式共通)**

| offset | 内容 |
|---|---|
| +0 | magic [u8;8] = "COLIGHT\0" |
| +8 | format [u8;4] = "CUML" または "CNTS"(FourCC) |
| +12 | version u32 = 1(形式ごとに1から採番) |
| +16 | entry_count u64 |
| +24 | 表セクションオフセット u64(= 64) |
| +32 | 部分seed配列オフセット u64 |
| +40 | checksum u64(表セクション+部分seed配列のFNV-1a64、この順) |
| +48 | CNTS: Rice符号化パラメータk(u8)。生成時に全体サイズが最小になる値を選び記録する(CUMLでは未使用、0のまま) |
| +49〜63 | 予約(= 0) |

**CUML(累積形式)**: オープン時のロードが不要で、検索は表を2箇所seekするだけで完結する。

| セクション | 内容 | サイズ |
|---|---|---|
| 累積和表 | プレフィックスP(24⁵通り)ごとのエントリ数の累積和(u32、LE)。要素iの値は「P<=iであるエントリ数の総和」 | 31,850,496B |
| 部分seed配列 | エントリ順にキー計算起点(1戦目開始時点)のseedの上位16bit(uint16) | entry_count×2B |

entry_count=128,095,165(本番実績)のとき合計288,040,890B(約275MiB)。

**CNTS(個数形式)**: ファイルサイズが最小になる代わりに、オープン時に個数列をロードし線形1パスで復号してチェックポイント(一定間隔ごとに累積エントリ数と符号列中のビット位置を記録した点)を構築する必要がある。

個数列の設計根拠: 実測によるとプレフィックスPごとの個数countの分布は16近傍の釣鐘型(平均16.1、最小1、最大43)で、エントロピーは約4.05bit/個。
また隣接プレフィックス間の個数の相関は0.011とほぼ独立であり、前値からの差分(デルタ)符号化によるメリットは見込めないため不採用とし、固定中心16からの残差を符号化する方式を採る。

| セクション | 内容 | サイズ |
|---|---|---|
| 個数列 | プレフィックスPごとのエントリ数countについて、残差r = count − 16(中心値16は仕様上の固定値)をzigzagマッピング(z = (r<<1)^(r>>31)。0,−1,1,−2,…→0,1,2,3,…)で非負整数化し、Rice符号(パラメータk)で符号化した列。Rice符号は商q = z>>kを単項符号(q個の1に続く0)、続けて剰余の下位kビットの順。ビット列はLSBファーストでバイト詰めし、末尾は8B境界まで0詰めする | 可変長(実測約3.9MB) |
| 部分seed配列 | エントリ順にキー計算起点(1戦目開始時点)のseedの上位16bit(uint16) | entry_count×2B |

kは生成時に全体サイズが最小になる値を選びヘッダ+48に記録する(本番データではk=2)。
個数列のセクション長は可変になるが、部分seed配列の位置はヘッダの+32オフセットで示されるため問題ない。

entry_count=128,095,165(本番実績)のとき、個数列は約3.9MBとなり、ファイル合計は260,314,978バイトになる。

部分seedに格納するのは、現行DBの値(生成後の状態)ではなく、キー計算の**起点**である(両形式共通)。
検証は起点から前向きにシミュレートしてキーを再現する方式であるため、起点でなければ成立しない。
検索の出力は、現行DBと同じ「生成後のseed」を返す仕様を維持する。

エントリはキーKの昇順に格納する。
CUMLは累積和表からPに対応するエントリ範囲を2箇所のseekで直接得られる。
CNTSは個数列から検索側でチェックポイントを構築することでPに対応するエントリ範囲が求まる。
範囲内(平均16.1エントリ)の全エントリについて下位16bit全探索+前向きシミュレートで検証する(Rはファイルに保存しないため絞り込みには使わず、最終照合のみで判別する)。

## 検索アルゴリズム

オープン時の準備(形式依存):

- **CUML**: ロード不要。プレフィックス表をseekするだけのゼロロード検索が可能
- **CNTS**: 個数列(実測約4.0〜4.3MB)をメモリにロードし、先頭から線形1パスでRice復号しながら、一定間隔ごとにチェックポイント(その時点までの累積エントリ数、および符号列中のビット位置)を構築する。検索時は対象P以下で直前のチェックポイントを起点に、そこからPまでの残り分だけをブロック内復号して区間[lo, hi)を得る

区間取得後の照合(下位16bit全探索+前向きシミュレート)は両形式で共通。

入力: 観測8回分のコード(先頭1回は捨てる)

1. c₁..c₅からPを計算する
2. Pに対応する範囲[lo, hi)を求める(平均16.1エントリ)
   - CUML: 累積和表を2箇所seekして直接得る
   - CNTS: 構築済みのチェックポイントから対象Pまでをブロック内復号して求める
3. 範囲内の**全エントリ**について、部分seed(上位16bit)の下位16bitを全探索して検証する
   - 候補v = (上位16bit ‖ x)、x∈[0, 2^16)
   - vから7回分をシミュレートし、コード列がc₁..c₇と一致するか確認する(generate_team_checked)
   - 自チームindexと自トレーナー名を都度判定し、一致しなければ早期棄却
4. 一致したvに対し、7回生成後のseedを返す

R(c₆, c₇)による絞り込みを行わないため、範囲内の全エントリに対して全探索+全照合を行う。
最終照合が7コード全てに対する完全一致であるため、誤検出は発生しない。

検証コストの見積り(1エントリあたり ≈ 7×10⁶ステップ):

| 段階 | 候補数 | 消費 | 演算量 |
|---|---|---|---|
| 自チームindex判定 | 65,536 | ~2.2 | 1.4×10⁵ |
| 敵パーティ + 名前 | 8,192 | ~632 | 5.2×10⁶ |
| 自パーティ | 2,731 | ~630 | 1.7×10⁶ |
| 2回目以降 | 114 → 5 → … | ~1,270 | 1.5×10⁵ |
| **合計** | | | **≈7×10⁶ステップ** |

範囲平均16.1エントリ × 1エントリあたり約7×10⁶ステップ ≈ 1.1×10⁸ステップ。
シングルスレッドで**数十ms〜100ms級**であり、1秒要件を十分に満たす。
キー空間24⁷ ≈ 2^32.07に対する完全照合のため誤検出は実用上発生しない。
クエリあたりの一致エントリ数は平均1件強。

## データベース構築(全再生成)

LCGの軌道(全周期2^32)を順に1回だけたどる「LCG軌道順走査+スライディングウィンドウ」方式でエントリを列挙する。
像判定・キー合成・(K, 起点seed)の生成を軌道走査と同時に行うため、像の再列挙や像ごとの再生成といった追加パスは発生しない。
方式の詳細・根拠・並列分割は`docs/design-orbit-scan.md`を参照。

エントリ列挙後、(K, 起点seed)をK昇順にソートし、新フォーマット(CUMLまたはCNTS)で書き出す(1.28×10⁸ 件 × 12 B ≈ 1.5 GB、メモリ内ソート可能)。

### 整合性検証

- エントリ数が現行DBの128,095,165と一致することを確認する(生成ロジックが同一なら像は同一集合になるはず)
- ランダムな状態から観測列を生成し、新旧検索処理の検索結果(生成後のseed)が一致することを確認する

## 実装状況

上記設計に基づき実装済み(`src/clight.rs`、コアのチーム生成ロジックは`src/teamgen.rs`に分離)。
正確なファイルレイアウトは`src/clight.rs`冒頭のdocコメントを正とする(本節の設計は概要)。

CUML・CNTSの両形式を実装済み。
CNTSの個数列セクションは本節「フォーマット仕様」記載のRice符号化+zigzag方式で実装済み。

サブコマンド:

- `codb-gen gen-light --out <FILE> [--limit <N>] [--threads <N>]`: 圧縮フォーマット(CNTS)での生成。limitの意味は`docs/design-orbit-scan.md`参照(既定は2^32、全周期)
- `codb-gen query <FILE> (<c1..c7>|<c0..c7>|--from-seed <HEX>)`: 検索(CUML/CNTSいずれのファイルも読める)
- `codb-gen verify-light <FILE>`: エントリ数・チェックサム・単調性の検証
- `codb-gen convert <IN> <OUT> <cuml|cnts>`: CUML/CNTS間の双方向変換

検証済み事項:

- 全2^32状態を対象とする本番生成が完走し、dedup後128,095,165エントリで現物LightDBと完全一致
- `convert`によるCUML/CNTS相互変換は往復(cnts→cuml→cnts)でバイト完全一致
- ランダム20seedの観測列で`query`が全件HITし、C#実物Searcher(`PokemonCOSeedDataBaseAPI`、現物LightDB)で検索した結果と全件一致
- 本番ファイルは`out/lightdb-cuml.cldb`(288,040,890バイト)・`out/lightdb-cnts.cldb`(260,314,978バイト、いずれも128,095,165エントリ)。`verify-light` OK

検証の詳細な再実行手順・ベンチマーク実測値は`HANDOFF.md`を参照。
