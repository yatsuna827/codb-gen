# LightDB 圧縮フォーマット 設計・見積

## 目的

ポケモンコロシアム「とにかくバトル」による現在seed特定に用いる LightDB について、
検索レイテンシ1クエリ1秒以内を満たしつつストレージサイズを削減する。

## 前提

### 観測モデル

- 対象: とにかくバトル(シングル・最強)
- 1回の観測で得られる情報: COMトレーナー名(3通り) × 自パーティ(8通り) = 24通り ≈ 4.585 bit
- 敵チームは画面に表示されないため観測に使用できない
- LCG の状態空間は 2^32 であり、log₂₄(2^32) ≈ 6.98 から理論上7回の観測で特定可能
- 運用上は8回観測し、先頭1回分を捨てて後ろ7回分をキーとする

### 現行 LightDB の構造(実測値)

| 項目 | 値 |
|---|---|
| ファイル数 | 576(観測 2 回分のコード 24² で分割) |
| 合計サイズ | 1,024,761,320 バイト(≈ 0.95 GiB) |
| エントリ形式 | key(uint32) + seed(uint32) = 8 バイト |
| エントリ数 | 128,095,165 |
| 値の意味 | キーになっている7回分のチームの**生成後**の LCG 状態(検索結果をそのまま現在 seed として使用可能) |

キーの計算起点は「観測1戦目開始時点の状態」だが、エントリに記録されているのは起点ではなく生成後の状態である点に注意する。

## 新フォーマット仕様

単一ファイル構成とする。
現行の576分割はキー先頭2個分をファイルシステムに逃がす一段目のインデックスとして機能していたが、
新フォーマットではインデックスを陽に持つため不要となる。

キーの定義: 観測 1〜7 戦目のコード c₁..c₇(各 [0,24)、c = トレーナー名 × 8 + チーム)に対し

```
K = c₁·24⁶ + c₂·24⁵ + c₃·24⁴ + c₄·24³ + c₅·24² + c₆·24 + c₇
P = ⌊K / 576⌋   (プレフィックス: c₁..c₅、24⁵ = 7,962,624 通り)
R = K mod 576   (剰余: c₆, c₇、10 bit で表現可能。ファイルには保存しない。
                 検索時は前向きシミュレートの全照合で判別する)
```

圧縮LightDBは対等な兄弟形式として**CUML(累積形式)**と**CNTS(個数形式)**の2種類を持つ。
格納内容そのものが呼称であり、優劣ではなくトレードオフの選択肢である。
ヘッダはmagic("COLIGHT\0")で両形式共通のファミリーを識別しつつ、format(FourCC "CUML"/"CNTS")で
形式を、version(形式ごとに1から採番)で形式内の改訂を表す。

ファイルレイアウト(リトルエンディアン、両形式とも「ヘッダ+表セクション+部分seed配列」の
3セクション構成で、表セクションの内容だけが異なる):

**ヘッダ(64B、両形式共通)**

| offset | 内容 |
|---|---|
| +0 | magic [u8;8] = "COLIGHT\0" |
| +8 | format [u8;4] = "CUML" または "CNTS"(FourCC) |
| +12 | version u32 = 1(形式ごとに1から採番) |
| +16 | entry_count u64 |
| +24 | 表セクションオフセット u64(= 64) |
| +32 | 部分seed配列オフセット u64 |
| +40 | checksum u64(表セクション+部分seed配列のFNV-1a64、この順) |
| +48〜63 | 予約(= 0) |

**CUML(累積形式)**: オープン時のロードが不要で、検索は表を2箇所seekするだけで完結する。

| セクション | 内容 | サイズ |
|---|---|---|
| 累積和表 | プレフィックスP(24⁵通り)ごとのエントリ数の累積和(u32、LE)。要素iの値は「P<=iであるエントリ数の総和」 | 31,850,496B |
| 部分seed配列 | エントリ順にキー計算起点(1戦目開始時点)のseedの上位16bit(uint16) | entry_count×2B |

entry_count=128,095,165(本番実績)のとき合計288,040,890B(約275MiB)。

**CNTS(個数形式)**: ファイルサイズが最小になる代わりに、オープン時に個数列をロードし
検索のたびに累積和(またはアンカー)を構築する必要がある。

| セクション | 内容 | サイズ |
|---|---|---|
| 個数列 | プレフィックスPごとのエントリ数を6bitずつビットパックした列(LSBファースト)。**値の上限63がフォーマット制約**(実測最大43、平均16.1。生成・変換時にassertで保証) | 5,971,968B |
| 部分seed配列 | エントリ順にキー計算起点(1戦目開始時点)のseedの上位16bit(uint16) | entry_count×2B |

entry_count=128,095,165(本番実績)のとき合計262,162,362B(約250MiB)。

部分seedに格納するのは、現行DBの値(生成後の状態)ではなく、キー計算の**起点**である(両形式共通)。
検証は起点から前向きにシミュレートしてキーを再現する方式であるため、起点でなければ成立しない。
検索の出力は、現行DBと同じ「生成後のseed」を返す仕様を維持する。

エントリはキーKの昇順に格納する。CUMLは累積和表からPに対応するエントリ範囲を2箇所のseekで
直接得られる。CNTSは個数列から検索側で累積和(またはアンカー)を構築することでPに対応する
エントリ範囲が求まる。範囲内(平均16.1エントリ)の全エントリについて下位16bit全探索+
前向きシミュレートで検証する(Rはファイルに保存しないため絞り込みには使わず、最終照合のみで
判別する)。

## 5. 検索アルゴリズム

オープン時の準備(形式依存):

- **CUML**: ロード不要。プレフィックス表をseekするだけのゼロロード検索が可能
- **CNTS**: 個数列(≈6MB)をメモリにロードし、累積和を構築する。構築方法は実装の自由であり、
  例えば次のいずれでもよい
  - (a) フル累積和: 個数列から24⁵要素のuint32累積和配列を構築する(≈32MB)。以降は
    各Pに対応する範囲をO(1)で参照できる
  - (b) 個数列+アンカー: 個数列本体(≈6MB)に加え、一定間隔(例: 256個ごと)でuint32の
    累積値アンカーを持たせる(≈6.1MB)。参照時はアンカーから対象Pまで個数列を加算していく
    (平均128回/引き)

区間取得後の照合(下位16bit全探索+前向きシミュレート)は両形式で共通。

入力: 観測8回分のコード(先頭1回は捨てる)

1. c₁..c₅からPを計算する
2. Pに対応する範囲[lo, hi)を求める(平均16.1エントリ)
   - CUML: 累積和表を2箇所seekして直接得る
   - CNTS: 構築済みの累積和(またはアンカー+残差)から求める
3. 範囲内の**全エントリ**について、部分seed(上位16bit)の下位16bitを全探索して検証する
   - 候補v = (上位16bit ‖ x)、x∈[0, 2^16)
   - vから7回分をシミュレートし、コード列がc₁..c₇と一致するか確認する(generate_team_checked)
   - 自チームindexと自トレーナー名を都度判定し、一致しなければ早期棄却
4. 一致したvに対し、7回生成後のseedを返す

R(c₆, c₇)による絞り込みを行わないため、範囲内の全エントリに対して全探索+全照合を行う。
最終照合が7コード全てに対する完全一致であるため、誤検出は発生しない。

検証コストの見積り(1エントリあたり ≈ 7×10⁶ ステップ):

| 段階 | 候補数 | 消費 | 演算量 |
|---|---|---|---|
| 自チーム index 判定 | 65,536 | ~2.2 | 1.4×10⁵ |
| 敵パーティ + 名前 | 8,192 | ~632 | 5.2×10⁶ |
| 自パーティ | 2,731 | ~630 | 1.7×10⁶ |
| 2回目以降 | 114 → 5 → … | ~1,270 | 1.5×10⁵ |
| **合計** | | | **≈ 7×10⁶ ステップ** |

範囲平均16.1エントリ × 1エントリあたり約7×10⁶ステップ ≈ 1.1×10⁸ステップ。
シングルスレッドで**数十ms〜100ms級**であり、1秒要件を十分に満たす。
キー空間 24⁷ ≈ 2^32.07 に対する完全照合のため誤検出は実用上発生しない。
クエリあたりの一致エントリ数は平均1件強。

## データベース構築(全再生成)

### 再生成手順

1. 全 2^32 状態に生成処理を1回適用し、像(約 1.28×10⁸ 状態)を列挙・重複排除する
2. 像の各seed(起点)から7回分のコードを生成し、キー K を得る
3. (K, 起点seed)を K 昇順にソートし、新フォーマット(CUMLまたはCNTS)で書き出す (1.28×10⁸ 件 × 12 B ≈ 1.5 GB、メモリ内ソート可能)

### コスト

- 像の列挙: 2^32 × 約 1,300 消費 ≈ 5.6×10¹² ステップ
- キー計算: 1.28×10⁸ × 約 9,000 消費 ≈ 1.15×10¹² ステップ
- 合計 ≈ 6.7×10¹² ステップ。16 スレッドの CPU で **10〜20 分程度**の一回きりの処理

### 整合性検証

- エントリ数が現行DBの 128,095,165 と一致することを確認する (生成ロジックが同一なら像は同一集合になるはず)
- ランダムな状態から観測列を生成し、新旧検索処理の検索結果 (生成後のseed)が一致することを確認する

## 実装状況

上記設計に基づき実装済み(`src/clight.rs`、コアのチーム生成ロジックは `src/teamgen.rs` に分離)。
正確なファイルレイアウトは `src/clight.rs` 冒頭のdocコメントを正とする(本節の設計は概要)。

CUML(累積形式)・CNTS(個数形式)の両形式を実装済みで、版数ではなく対等な兄弟形式として運用している。

サブコマンド:

- `codb-gen gen-light --out <FILE> [--limit N] [--threads N]`: 圧縮フォーマット(CNTS)での生成
- `codb-gen query <FILE> (<c1..c7>|<c0..c7>|--from-seed <HEX>)`: 検索(CUML/CNTSいずれのファイルも読める)
- `codb-gen verify-light <FILE>`: エントリ数・チェックサム・単調性の検証
- `codb-gen convert <IN> <OUT> <cuml|cnts>`: CUML/CNTS間の双方向変換

検証済み事項:

- 全2^32状態を対象とする本番生成が完走し、dedup後128,095,165エントリで現物LightDBと完全一致
- `convert`によるCUML/CNTS相互変換は往復(cnts→cuml→cnts)でバイト完全一致
- ランダム20seedの観測列で`query`が全件HITし、C#実物Searcher(`PokemonCOSeedDataBaseAPI`、
  現物LightDB)で検索した結果と全件一致
- 本番ファイルは `out/lightdb-cuml.cldb`(288,040,890バイト)・`out/lightdb-cnts.cldb`
  (262,162,362バイト、いずれも128,095,165エントリ)。`verify-light` OK

検証の詳細な再実行手順・ベンチマーク実測値は `HANDOFF.md` を参照。
