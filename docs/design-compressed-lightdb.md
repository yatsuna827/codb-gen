# LightDB 圧縮フォーマット 設計・見積

## 目的

ポケモンコロシアム「とにかくバトル」による現在seed特定に用いる LightDB について、
検索レイテンシ(ミリ秒級)を維持したままストレージサイズを削減する。

## 前提

### 観測モデル

- 対象: とにかくバトル(シングル・最強)
- 1回の観測で得られる情報: COMトレーナー名(3通り) × 自パーティ(8通り) = 24通り ≈ 4.585 bit
- 敵チームは画面に表示されないため観測に使用できない
- LCG の状態空間は 2^32 であり、log₂₄(2^32) ≈ 6.98 から理論上7回の観測で特定可能
- 運用上は8回観測し、先頭1回分を捨てて後ろ7回分をキーとする

### 現行 LightDB の構造(実測値)

| 項目 | 値 |
|---|---|
| ファイル数 | 576(観測 2 回分のコード 24² で分割) |
| 合計サイズ | 1,024,761,320 バイト(≈ 0.95 GiB) |
| エントリ形式 | key(uint32) + seed(uint32) = 8 バイト |
| エントリ数 | 128,095,165 |
| 値の意味 | キーになっている7回分のチームの**生成後**の LCG 状態(検索結果をそのまま現在 seed として使用可能) |

キーの計算起点は「観測1戦目開始時点の状態」だが、エントリに記録されているのは起点ではなく生成後の状態である点に注意する。

## 新フォーマット仕様

単一ファイル構成とする。
現行の576分割はキー先頭2個分をファイルシステムに逃がす一段目のインデックスとして機能していたが、
新フォーマットではインデックスを陽に持つため不要となる。

キーの定義: 観測 1〜7 戦目のコード c₁..c₇(各 [0,24)、c = トレーナー名 × 8 + チーム)に対し

```
K = c₁·24⁶ + c₂·24⁵ + c₃·24⁴ + c₄·24³ + c₅·24² + c₆·24 + c₇
P = ⌊K / 576⌋   (プレフィックス: c₁..c₅、24⁵ = 7,962,624 通り)
R = K mod 576   (剰余: c₆, c₇、10 bit で表現可能)
```

ファイルレイアウト(リトルエンディアン):

| セクション | 内容 | サイズ |
|---|---|---|
| ヘッダ | マジックナンバー、バージョン、エントリ数、各セクションのオフセット、チェックサム | 64 B 程度 |
| プレフィックス表 | プレフィックス P ごとの累積エントリ数(uint32 × 24⁵) | ≈ 32 MB |
| キー剰余配列 | エントリ順に R(10 bit)をビットパック | ≈ 160 MB |
| 部分 seed 配列 | エントリ順に**キー計算起点(1 戦目開始時点)の seed** の上位 16 bit(uint16) | ≈ 256 MB |

**合計 ≈ 450 MB**(現行比で約半分)。

部分seedに格納するのは、現行DBの値(生成後の状態)ではなく、キー計算の**起点**である。
検証は起点から前向きにシミュレートしてキーを再現する方式であるため、起点でなければ成立しない。
検索の出力は、現行DBと同じ「生成後のseed」を返す仕様を維持する。

エントリはキー K の昇順に格納する。
プレフィックス表により P に対応するエントリ範囲が O(1) で求まり、範囲内(平均16.1エントリ)を剰余 R で線形照合する。

補足: キー剰余配列とプレフィックス表をElias-Fano符号に置き換えると約370MBまで削減できる。あとでやる。

## 5. 検索アルゴリズム

入力: 観測8回分のコード(先頭1回は捨てる)

1. c₁..c₇ から K, P, R を計算する
2. プレフィックス表から該当範囲を求め、剰余配列を照合して一致エントリを得る
3. 一致エントリごとに、部分seed(上位16bit)の下位16bitを全探索して検証する
   - 候補 v = (上位 16 bit ‖ x)、x ∈ [0, 2^16)
   - v から7回分をシミュレートし、コード列が c₁..c₇ と一致するか確認する
   - 自チームindexと自トレーナー名を都度判定し、一致しなければ早期棄却
4. 一致した v に対し、7回生成後のseedを返す

検証コストの見積り(一致エントリ1件あたり):

| 段階 | 候補数 | 消費 | 演算量 |
|---|---|---|---|
| 自チーム index 判定 | 65,536 | ~2.2 | 1.4×10⁵ |
| 敵パーティ + 名前 | 8,192 | ~632 | 5.2×10⁶ |
| 自パーティ | 2,731 | ~630 | 1.7×10⁶ |
| 2回目以降 | 114 → 5 → … | ~1,270 | 1.5×10⁵ |
| **合計** | | | **≈ 7×10⁶ ステップ** |

シングルスレッドで**数ミリ秒**。
キー空間 24⁷ ≈ 2^32.07 に対する完全照合のため誤検出は実用上発生しない。
クエリあたりの一致エントリ数は平均1件強。

## データベース構築(全再生成)

### 再生成手順

1. 全 2^32 状態に生成処理を1回適用し、像(約 1.28×10⁸ 状態)を列挙・重複排除する
2. 像の各seed(起点)から7回分のコードを生成し、キー K を得る
3. (K, 起点seed)を K 昇順にソートし、新フォーマットで書き出す (1.28×10⁸ 件 × 12 B ≈ 1.5 GB、メモリ内ソート可能)

### コスト

- 像の列挙: 2^32 × 約 1,300 消費 ≈ 5.6×10¹² ステップ
- キー計算: 1.28×10⁸ × 約 9,000 消費 ≈ 1.15×10¹² ステップ
- 合計 ≈ 6.7×10¹² ステップ。16 スレッドの CPU で **10〜20 分程度**の一回きりの処理

### 整合性検証

- エントリ数が現行DBの 128,095,165 と一致することを確認する (生成ロジックが同一なら像は同一集合になるはず)
- ランダムな状態から観測列を生成し、新旧検索処理の検索結果 (生成後のseed)が一致することを確認する
