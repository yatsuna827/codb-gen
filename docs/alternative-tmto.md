# 代替案: 時間空間トレードオフ(Hellman テーブル / レインボーテーブル)

## 1. 概要

一方向関数の逆算に用いられる古典的な時間空間トレードオフ(TMTO)を適用する方式。
数百 MB のテーブルで全 2^32 状態を確率的にカバーし、クエリ時に一定の計算を行う。

## 2. 定式化

関数 f を次のように定義する。

```
f(s) = s を起点とする 7 バトル分のコード列 (c₁..c₇) を整数化した値
       K = Σ cᵢ·24^(7-i) を 32 bit に縮約したもの
```

f は 32 bit → 32 bit の擬似ランダム関数とみなせる。観測から K が得られるため、
「f(s) = K なる s を求める」という関数逆算問題に帰着し、TMTO が適用できる。

チェーン構成(レインボーテーブル、チェーン長 t、チェーン本数 m):

- 縮約関数 Rᵢ(列位置ごとに異なる)で f の出力を次の入力に写す
- テーブルには各チェーンの始点・終点のみを保存する

パラメータ例: t = 2^8、m = N/t = 2^24 とすると、テーブルは 2^24 × 8 B = **128 MB**。

## 3. コスト解析

### クエリ

- 探索: 最大 t 回の再構築 × 平均 t/2 回の f 評価 ≈ t²/2 = 32,768 回
- f 1 回 ≈ 7 バトル ≈ 9,000 消費であるから、約 3×10⁸ ステップ
- シングルスレッドで **0.1〜0.3 秒**(偽アラーム検証で 2〜3 倍のばらつきあり)
- 列単位で独立なため並列化は容易

### テーブル生成

- m × t = N 回の f 評価 ≈ 2^32 × 9,000 ≈ 3.9×10¹³ ステップ
- 16 スレッドの CPU で 30 分前後、GPU なら数分
- ただし単一テーブルの被覆率は理論上 80% 台で頭打ちになるため、
  実用的な成功率(99% 以上)には複数テーブルまたは余裕を持たせた構成が必要であり、
  生成コストとメモリは数倍(**256〜512 MB、CPU 数時間**)を見込む

## 4. 評価

### 長所

- 全 2^32 を対象としつつテーブルが数百 MB に収まる
  (像への制限や観測の先頭 1 回の破棄が不要)
- 逆算問題としての定式化は汎用的で、他タイトルへの転用が利く

### 短所

- 検索成功が確率的(テーブルを増やしても 100% にはならない)
- クエリレイテンシ 0.1〜0.3 秒は、圧縮 LightDB 案(数 ms)に対して 2 桁劣る
- 偽アラーム処理・縮約関数設計・複数テーブル管理など実装の複雑さが最も高い
- メモリを実用水準まで積むと、結局サイズが圧縮 LightDB 案(約 450 MB)と同等になる

## 5. 結論

検索が確率的に失敗するのは論外。
