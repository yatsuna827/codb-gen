# LCG軌道順走査+スライディングウィンドウ 設計

## 目的

圧縮LightDB生成(`gen-light`)のエントリ列挙方式。
全状態への1回チーム生成の適用結果をビットマップに記録してから像だけを拾い直す方式(ランダムアクセスのRMWが2^32回)、および像ごとにキー用の7回分を再生成する方式(像の数だけ7回分の生成をやり直す)をどちらも使わず、LCGの軌道を順番に1回だけ走査しながら、像判定とキー合成をその場で完結させる。
ランダムアクセスも再生成もないため、状態あたりの平均消費量(1回のチーム生成につき約1,265回のrand呼び出し)を除けば、各状態の処理は定数時間になる。

出力されるエントリ集合は列挙順序に依存しないため、Phase3(ソート+dedup)以降の決定的なパイプラインを経て、既存の生成結果とバイト完全に一致する(`docs/design-compressed-lightdb.md`参照)。

## 根拠となる事実

- GC LCG(`s' = s*A + B mod 2^32`)は乗数Aが奇数であり全周期2^32を持つ。すなわちseed 0から1ステップずつ辿る軌道 `s_0=0, s_1, s_2, ...` は状態空間の全状態をちょうど1回ずつ訪れる巡回列になる
- チーム生成 `f` は状態sからn(s)回(平均約1,265回、裾の長い分布)のrand呼び出しを消費し、内部で1ステップずつ状態を進めるので、軌道上の位置jにおける像は`f(s_j) = s_{j+n_j}` と、軌道上の少し先の位置に一致する
- したがって軌道順に位置jを走査しながらn_jを求めれば、「位置jが像かどうか」はビットマップへのランダムアクセスではなく「位置j+n_jへフラグを立てる」という局所的な書き込みだけで判定できる
- 像のキーK(観測7回分のコードc1..c7)と7回チーム生成後のseedは、軌道上をi → i+n_i → i+n_i+n_{i+n_i} → … と7ホップ辿るだけで合成できる(i回目のホップで得られるコードがc_{i+1}に対応する)

## リングバッファとスライディングウィンドウ

軌道上の各位置pについて、コードc(u8)・消費数n(u16)・状態s(u32、その位置での軌道の値そのもの)・状態sの上位16bit(u16、`ring.hi`。テーブル駆動生成が読む乱数値。後述「乱数値列のu16化」参照)・像フラグ(bool)をリングバッファ(SoAの5配列)に記録する。
位置pのスロットは`p & (RING-1)`。

| 定数 | 値 | 役割 |
|---|---|---|
| `RING` | `1<<18` (262,144) | リングバッファの物理スロット数 |
| `LAG` | `1<<17` (131,072) | 解決までの遅延 |
| `PROLOGUE` | `1<<16` (65,536) | 像フラグの伝播元がありうる範囲 |
| `LEAD` | `1<<14` (16,384) | 状態列`ring.s`を生成位置より先行書き込みする量(後述の高速化で使用) |

走査位置pで1回だけチーム生成し、コードc、消費数n、状態sを記録したのち、像フラグを位置`p+n`のスロットに立てる(そのスロットのc/n/sはまだ未記入のまま)。
その後、pをLCGで1ステップだけ進めて次の位置へ移る。

pが位置`j+LAG`に達した時点で位置jを**解決**する。
像フラグが立っていれば、jから7ホップ辿ってコード7個(先頭がc1)からキーKを、終端位置の状態を7回チーム生成後のseedとして組み立て、s_jを起点としたエントリを作る。
ホップ先が未走査の位置に達してしまう場合は、平均ホップ距離が約8,850でLAGに対して十分小さいため実質発生しないが、s_jから素直にチーム生成を7回呼び直すフォールバックで解決する。
解決した位置の像フラグはその場でクリアし、スロットの再利用に備える。

1回のチーム生成の消費数nがu16に収まることをassertする(平均1,265、u16を超える確率は事実上ゼロ)。
これはPROLOGUEの妥当性(後述)の前提でもある。

### スロット再利用の安全性

物理スロット`p & (RING-1)`は論理位置`p, p+RING, p+2*RING, ...`で使い回される。
以下の順序が常に成り立つように定数を選んである(`PROLOGUE < RING-LAG`が根拠。`RING=2^18`, `LAG=2^17`, `PROLOGUE=2^16`なので`RING-LAG=2^17 > PROLOGUE=2^16`):

```
位置p-RINGの解決時クリア(時刻 (p-RING)+LAG = p-(RING-LAG))
  → pへの像フラグ書き込み(最速で時刻 p-PROLOGUE)
  → pの走査(時刻 p)
  → pの解決(時刻 p+LAG)
```

位置jの像フラグを立てうる前任位置iはj-PROLOGUE超j以下に限られる(nのu16 assertが保証する)。
新しい論理位置pのためのフラグ書き込みが起こりうる最速の時刻(p-PROLOGUE)は、前の使用者(論理位置p-RING)の解決時クリア(時刻p-(RING-LAG))より必ず後になるため、フラグが混線することはない。

## 並列分割

スレッドT個で軌道を等長のT個の弧に分割する。
弧の起点状態は、seed 0から任意ステップ数だけ進める汎用のLCGジャンプ関数(`teamgen::lcg_jump`。乗数・加数の対を繰り返し二乗して合成する、O(log k)の標準的な方法)で直接求める。

各スレッドは以下の範囲を走査する(弧を`[arc_start, arc_end)`とする):

1. **プロローグ**: `[arc_start-PROLOGUE, arc_start)`。像フラグを弧内へ伝播させるためだけに走査する。位置jの像フラグを立てうる前任位置はj-PROLOGUE超j以下に限られるため、プロローグを走査すれば弧の先頭への流入フラグが過不足なく揃う
2. **弧本体**: `[arc_start, arc_end)`。通常どおり走査・解決し、エントリを作る
3. **エピローグ**: 弧本体の走査だけでは末尾付近の解決に必要なホップ参照先データが揃わないため、pが`arc_end+LAG`に達するまで(弧内の全位置が解決されるまで)走査を続ける。この区間はc/n/sの記録とホップ参照のみに用い、新たに伝播した像フラグが弧外の位置に立ってもそれを解決するのは次の弧の役目であり、この弧では解決しない

プロローグ区間は隣接する前の弧の弧本体と位置が重なるが、エントリを作るのは「解決した位置がその弧自身の`[arc_start, arc_end)`に入っているときだけ」という条件で弧ごとに1回に限定されるため、重複生成は起こらない。
この結果、各スレッドは独立したリングバッファを持てばよく、スレッド間の同期は不要になる。
バケツへの集約はスレッドローカル24バケツをMutexでマージする方式を踏襲する。

## オンライン自己検査

解決した位置jが像であり、かつ`s_j & 0xFFF == 0`のとき(全周期を通じて決定的なサンプル数になる)、s_jから素直にチーム生成を7回呼び直してキーKと7回生成後seedを再計算し、リングバッファのホップで合成した結果と照合する。
不一致ならs_j・両者の値を出力してpanicする。
常時有効とし、オーバーヘッドは無視できる水準(0.1%未満)に収まる。

## limitの意味

`gen-light`の`limit`は「seed 0を起点とする軌道の先頭limit位置」を指す。
数値としての先頭N個(状態0, 1, 2, ...)ではないことに注意する。
部分実行では、像フラグはプロローグを含めて実際に走査した範囲からしか立たないため、範囲の境界付近では本来像であるはずの位置が像として検出されないことがありうる(プロローグ・エピローグの分だけ余分に走査してこれを補っているが、limitで指定した範囲そのものの外側にある伝播元までは遡らない)。
`limit = 2^32`のときは全周期を走査するため、この境界効果は生じず、従来と同一の完全な出力になる。

## 検証方針

エントリ集合はキー計算に用いる状態集合(像)にのみ依存し、以降のPhase3(ソート+dedup)・Phase4(書き出し)は決定的であるため、全周期(`limit = 2^32`)での生成結果は既存の成果物(`out/lightdb-cuml.cldb` / `out/lightdb-cnts.cldb`)とバイト完全に一致するはずである。
全周期実行は数時間を要するため、日常的な検証は部分実行(スモークテスト)とオンライン自己検査、およびスレッド数を変えても出力がバイト一致することの確認で行い、全周期実行によるバイト一致確認は別途行う。

## 検討事項: 生成のインターリーブ化

`scan_arc`は1位置ずつ逐次にチーム生成しており、LCGの乗算依存チェーン(レイテンシ約4サイクル)がボトルネックになりうる。
対策として、連続するL位置を1バッチとし、バッチ内の各レーンを独立した状態から出発させ、チーム生成の各フェーズ(敵チーム決定→自チーム再抽選→敵TSV→敵6スロット→名前→自TSV→自6スロット)をレーン方向の内側ループでロックステップ実行する方式(再抽選ループは完了済みレーンをスキップするマスク方式)を試作した。
各レーンの状態は他レーンから一切参照されないため、フェーズをレーン単位でまとめて処理する順序の違いは結果(コード・消費数・終了状態)に影響せず、出力はスカラー版と同一になるはずである(実際、L=4/8/16のいずれでも生成結果はバイト完全一致した)。

しかし本機(Intel N150、Gracemont)での実測では、L=4/8/16のいずれもスカラー版より明確に遅くなった(フェーズごとに`[u32; L]`をレーン可変インデックスで読み書きする構造ではコンパイラがレジスタに保持しきれずスタック常駐になったとみられる。名前付きスカラー変数に手で展開したL=4版で確認しても、レジスタ常駐は改善したがそれでもスカラー版より遅く、このコアではレイテンシ隠蔽によるILP向上が得られなかった)。
そのため`scan_arc`は逐次版のまま採用し、インターリーブ化は見送った。

## 高速化: 乱数値の共有と再抽選のバッチ走査(採用済み)

上記インターリーブとは別の切り口で、走査部を約24%高速化した(本機・4スレッド・部分実行`limit=0x2000000`で走査16.9〜17.0秒 → 12.7〜13.1秒)。
出力はバイト完全に不変(スレッド数1/3/4で既存成果物とバイト一致)。
二段構えである。

### 乱数値の共有(テーブル駆動生成)

位置pのチーム生成が消費する乱数列は s_{p+1}..s_{p+n} の上位16bitそのもので、これはリングバッファの`ring.s`に格納している状態列と重複している。
そこで状態列`ring.s`の書き込みを生成位置より`LEAD`位置**先行**させ(位置pの走査時に`ring.s`が位置`p+LEAD`まで書き込み済みになるよう、ループ先頭で毎回`p+LEAD`のsを1ステップ進めて書く)、チーム生成を「`ring.s`を読むテーブル駆動」(`teamgen::generate_team_from_table`)に変える。
これにより生成内部の逐次LCG乗算チェーン(4サイクル/ステップのレイテンシ律速)が消える。

`LEAD`の安全性は`LEAD < RING-LAG(= 2^17)`にのみ依存する(値を小さくするほど安全側)。
s配列のスロット再利用は、`p+LEAD`への先行書き込みが上書きする旧論理位置`p+LEAD-RING`が、解決処理のホップ参照範囲`[p-LAG, p]`より古い(`p+LEAD-RING < p-LAG`⇔ `LEAD < RING-LAG`)ため混線しない。
hopが読む`ring.c`/`ring.n`の生存範囲はLAG/RINGのみで決まりLEAD非依存、PROLOGUE(像フラグ伝播)も真の消費数nに基づきLEAD非依存なので、LEADを変えても安全性・出力とも影響を受けない。

#### LEAD縮小によるキャッシュ局所性改善とフォールバック

当初`LEAD`は「1回のチーム生成の消費数nの上界(u16::MAX)以上」という安全マージンで`1<<16`(65,536)に取っていたが、実際のnは平均約1,265であり、位置pの生成が読む`ring.s[p+1..p+n]`はfillがp+65,536先の位置に書き込んでから読まれるまで約64,000反復も経つため、キャッシュから追い出されて必ずミスしていた。
これがボトルネックだったため、`LEAD`を平均nに近い値へ縮小し、fill(書き)と生成(読み)を時間的に近接させてL1/L2ヒットを狙う。
ただしn>LEADとなる(稀な)位置では生成が書き込み位置を追い越して古いデータを読んでしまうため、その位置だけ`teamgen::generate_team_from_table`が`None`を返し、呼び出し側がスカラー(`generate_team_with_count`)で再計算するフォールバックを設けた。

`generate_team_from_table`(および内部の`teamgen::gen_slot_table`)は、読み位置が`start_idx + lead`を超えるバッチ/レーンの受理を信用しないマスク処理を行い、書き込み位置を追い越す読みが発生した時点で`None`を返す。
フォールバックは真のn(u16::MAX以下)をスカラー計算で得るため、像フラグ・自己検査・emitするnはすべて正しい真値のままであり、**出力バイトはLEADの値によらず不変**(スレッド数1/3/4・複数のLEAD値でバイト完全一致を確認済み)。

本機(4スレッド・部分実行`limit=0x2000000`)での実測(phase1+2、複数回実行の最小値〜平均、フォールバック率):

| LEAD | 最小 | 平均目安 | フォールバック率 |
|---|---|---|---|
| 2,048 (`1<<11`) | 12.7s | 12.75s | 1.40% |
| 4,096 (`1<<12`) | 12.2s | 12.56s | 0.0001% |
| 8,192 (`1<<13`) | 12.3s | 12.64s | 0% |
| 16,384 (`1<<14`) | 12.1s | 12.52s | 0% |
| 32,768 (`1<<15`) | 12.4s | 12.65s | 0% |
| 65,536 (`1<<16`、旧設定) | 12.7s | 12.9s | 0% |

`LEAD`が小さすぎる(2,048)とフォールバック(スカラー再計算)の増加が支配的になり逆に遅くなる。
`LEAD=16,384`がフォールバック0%を保ちつつ最も速く、採用値とした(旧設定`1<<16`比で数%の追加改善。実測のばらつきが数百ms〜1秒程度あり、このスケールでの差は誤差に近い)。

**注意**: テーブル駆動化は単体では高速化にならない(本機ではテーブル読みのロードレイテンシが除去したはずの乗算チェーンとほぼ同等で差し引きゼロ)。
素朴に実装するとLLVMが後続スロットの乱数消費位置を起点idxからのアフィン式(idx+7, +14, ...)として先行計算し、再抽選ループでそれらを同時に多数保持するためレジスタが不足して大量のスタック退避を起こし、逆に約2.6倍悪化する。
真に効くのは次項のバッチ走査で、これがこのレジスタ不足を避けつつ自動ベクトル化を可能にする。

### 再抽選ループのバッチ走査(SIMD)

チーム生成の律速はポケモン1匹の生成(`gen_slot`)の再抽選ループで、乱数ペア(hi, lo)を引いて性格(`pid % 25`)・性別・色回避の条件を判定し、満たすまで繰り返す(平均で性格1/25が主フィルタ)。
テーブル駆動化で乱数がバッファ上の値になったので、この再抽選を**テーブル経路専用に**、`B`候補ずつ連続スライス上でまとめて評価する形(`teamgen::gen_slot_table`)に書き換える。

- 連続する`2*B`個の`ring.s`エントリを部分スライスとして取り、各候補jの受理判定を計算してビットマスクに詰め、`trailing_zeros`で**バッチ内の最初の受理候補**を得る。バッチは前から処理するため、スカラー版の「最初に受理する候補」と厳密に一致する(nとidxの最終値も一致)。
- リングの折り返し(`(idx+1) & mask` から`2*B`が`RING`境界をまたぐ)バッチだけ、1候補ずつのスカラーにフォールバックする。折り返しは`2^18`位置に1回程度なので影響は無視できる。
- バッチ内の受理候補より後ろのレーンは`ring.s`を余分に読むが、結果に使わないので無害(スライスは連続かつ`RING`境界内なのでメモリ安全。書き込み位置を超えた古い値を読みうるが破棄される)。

この形にするとレジスタ不足が起きず、かつLLVMがバッチ評価を自動ベクトル化してAVX2(ymm、`pid % 25`の乗算逆数化・`vpcmpgtd`/`vpcmpeqd`・8レーンのマスク)で走らせる。
`B`は8/16/32を実測して`B=16`が最良(本機)。
手書きAVX2組み込みは自動ベクトル化で既にymm化されるため不要。

スカラー経路(`generate_team`/`generate_team_checked`)は無変更で、`gen_slot`/`generate_team_impl`の汎用版をそのまま使う。
テーブル経路(`gen_slot_table`)は受理条件をこの汎用版と一致させて複製しており、両者の一致はオンライン自己検査(テーブル合成をスカラー再計算と照合)と部分実行のバイト一致で担保する。

なお`RUSTFLAGS="--emit asm"`はローカルの`.cargo/config.toml`の`target-cpu=native`を上書きしてしまいAVX2が無効化される。ベクトル化を確認する際は`RUSTFLAGS="-C target-cpu=native --emit asm"`と明示すること。

### 乱数値列のu16化(読み込みウィンドウの半減 / 2026-07-07採用)

上記のテーブル駆動生成が読むのは各位置の状態sの**上位16bit(乱数出力)だけ**である(`gen_slot_table`/`next_tab`はいずれも`s >> 16`しか使わない)。にもかかわらずリングには状態s(u32)を格納しており、ホットループはu32配列を読んでいた。

そこで状態列`ring.s`(u32、fillでのLCGステップとホップ解決の起点seed/最終seedに必要)とは別に、上位16bitだけを持つ**`ring.hi`(u16配列)**を並行して持ち、チーム生成(`generate_team_from_table`)はこの`ring.hi`を読むようにした。`ring.s`と`ring.hi`はfillで常に同じ位置に同時書き込みする(1位置あたりu16書き込みが1回増えるだけで、ホットループの平均約1,265読みに対し無視できる)。

効果はキャッシュ局所性で、読む要素あたりのバイト数が半分になる:

- 位置pの生成が読む範囲は`ring.hi[p+1..p+n]`で、生存ウィンドウは約`LEAD`要素。u32なら`LEAD=2^14`で約64KB(Gracemont/N150のL1D 32KBを溢れてL2)だったが、u16なら約**32KBでL1Dに収まる**。
- バッチ走査(`gen_slot_table`)が読む連続`2*B=32`要素は、u32では128B(2キャッシュライン)、u16では**64B(1キャッシュライン)**。ストリーミング読みの帯域も半減する。

`generate_team_from_table`/`gen_slot_table`/`next_tab`のシグネチャを`&[u16]`に変え、各読みの`>> 16`を除去(要素が既に上位16bit)しただけで、**読み出す値は完全に同一**なので出力バイトは不変。テーブル経路とスカラーの一致は従来どおりオンライン自己検査と部分実行のバイト一致で担保される(`table_path_matches_scalar`テストも`ring.hi`相当のu16列を作って照合するよう更新)。

本機(4スレッド・部分実行`limit=0x2000000`)でのphase1+2実測(u32版とu16版を交互に各4回):

| | u32(旧) | u16(新) |
|---|---|---|
| 走査時間 | 12.2 / 13.0 / 13.0 / 12.8s | 10.9 / 10.9 / 10.9 / 11.0s |
| 中央値 | 約12.9s | 約10.9s |

**走査が約15%高速化**(u16版は分散も小さい)。全周期`limit=2^32`の実測では走査1,584秒→**1,274秒(約19.6%短縮)**、生成全体で約26.5分→約21.3分。出力は`limit=0x2000000`・`0x1000000`のsha256一致および全周期の`out/lightdb-cnts.cldb`とのバイト完全一致(self-check 39,896件全通過・fallback 0%)で確認済み。

### バッチ境界チェックの高速パス化(2026-07-07採用)

`gen_slot_table`のバッチ走査は、受理判定`hits`を得たあと「書き込み位置`idx_limit`を追い越して古い値を読んでいないか」を毎バッチ検査していた(`valid = ((idx_limit - base)/2).min(B)`と`valid_mask`生成、減算・除算・シフト・分岐)。この検査結果`vhits`は`hits`の消費側(`trailing_zeros`と分岐)の手前に入るため、**バッチ間の直列レイテンシ鎖**(再抽選ループの律速)を毎バッチ数サイクル延ばしていた。

`LEAD=16,384`ではfallback率0%であり、大半のバッチは書き込み位置から遠い。そこで**バッチ全体が書き込み済み範囲に収まる場合(`base + 2*B <= idx_limit`)の高速パス**を分け、そこでは境界計算を一切せず`hits`を直接消費する。境界近傍(`base + 2*B > idx_limit`、このとき必ず`valid < B`)だけ従来のマスク処理に入り、受理が無ければ`None`(スカラー再計算)を返す。**論理は完全に等価**(高速パスは`valid = B`かつ`valid_mask`が全ビットの特殊ケース)で出力バイトは不変。

本機(4スレッド・`limit=0x2000000`)でのphase1+2実測(高速パス無/有を交互に各5回):

| | 高速パス無 | 高速パス有 |
|---|---|---|
| 走査時間 | 10.0 / 11.2 / 11.0 / 11.2 / 10.9s | 10.5 / 10.5 / 10.6 / 10.5 / 10.5s |
| 中央値 | 約11.0s | **約10.5s** |

境界計算をクリティカルパスから外したことで**走査が約4〜5%高速化し、実行ごとの分散もほぼ消えた**(10.5秒に張り付く)。

u16化と高速パス化を合わせた**全周期`limit=2^32`の最終実測**: 走査1,584秒→**1,242秒(約21.6%短縮)**、生成全体約26.5分→**20.8分**。出力は`out/lightdb-cnts.cldb`とバイト完全一致(self-check 39,896件全通過・fallback 0%)、部分実行のsha256一致でも確認済み。

### 試したが不採用: PGO(プロファイル誘導最適化)

`llvm-tools-preview`を入れ、`-Cprofile-generate`で計装ビルド→部分実行で訓練→`llvm-profdata merge`→`-Cprofile-use`で再ビルド、という2段PGOを試した(いずれも`target-cpu=native`併用)。結果は素のビルドと**測定差なし**(中央値約11.0s→約11.0s、ノイズ内)。
この走査の律速は分岐予測ミスではなく再抽選バッチのレイテンシ鎖であり、PGOが効く分岐レイアウト/インライン判断の余地がほぼ無いことの傍証。ビルド手順が2段になる割に得が無いため不採用。
